Databricks Skills in Platform MCP

How we make Databricks' official agent skills available to everyone who uses Platform MCP, including Claude Desktop users who never touch a terminal.

Author Joey Filichia Updated October 28, 2026 Status Decided: Databricks App (Option D) Analyzed platform-mcp@6675af1, databricks-agent-skills@v0.2.37

Summary

  • Databricks publishes 33 stable agent skills, structured guides that teach coding agents how to do Databricks work well. Today they install locally and assume a personal Databricks CLI login.
  • Platform MCP users reach Databricks through our gateway with server-side OAuth and read-only SQL and Genie. Most have no CLI, so most skills would tell them to run commands they can't run.
  • Decision: we'll build our own MCP server and host it as a Databricks App on the aplaceformom workspace. It serves a curated, APFM-adapted set of skills, plus a small set of typed, read-only tools built on the Databricks Python SDK. Platform MCP reaches it as a new server in its Databricks connection, and other clients can connect to it directly.
  • The app uses only the Python SDK and never runs the Databricks CLI. Each operation is its own tool with its own read or write level, and writes stay blocked until reviewed one by one.
  • Engineers who build and deploy on Databricks keep installing the official plugin locally.
  • Not yet verified: whether the app accepts the per-user token Platform MCP already holds, and whether the user's token reaches the app's code. Step 0 of the plan is a short spike to confirm both.

Background

Platform MCP today

Platform MCP is our Go gateway at platform-mcp.apfmtech.com/mcp/. Claude Code and Codex connect over HTTP, and Claude Desktop connects through the APFM connector. Each provider (AWS, GitHub, Atlassian, Databricks, and others) exposes a discover tool and a call tool. Access is checked on every request against the caller's role.

The Databricks provider forwards calls to Databricks' own MCP servers on the aplaceformom workspace. It uses per-user OAuth, so Unity Catalog permissions and audit logs apply to the actual person. Today it allows read-only SQL and seven Helix Care Genie spaces. Each server type is a short entry in servertypes.go that defines its URL and which tools are allowed.

databricks-agent-skills

This is Databricks' official repository of skills: 33 stable ones, about 3.3 MB of markdown, each with a SKILL.md and reference files. It covers SQL, Genie, Unity Catalog, apps, bundles, jobs, pipelines, Lakebase, model serving, and more. Engineers install it with databricks aitools install or a plugin marketplace. The plugins also ship hooks that steer the agent to the right skill. New releases arrive several times a week.

The gap

The skills were written for someone at a terminal with their own Databricks login. Our users mostly aren't.

The skills assumeA Platform MCP user has
A local databricks CLI with an authenticated profile. The core skill alone has 136 CLI commands.No CLI. Auth happens server-side. Desktop users have no shell at all.
Skills are files on disk that the agent picks up automaticallyMCP has no built-in skill concept. Content must be fetched with a tool and the agent must be told it exists.
Full read and write: deploy bundles, create jobs, apps, and endpointsRead-only SQL and Genie
Data questions go to databricks genie askData questions go to our configured Genie spaces through databricks_call

The app closes this gap in three ways: it delivers the skills over MCP, it adds a short APFM note to each skill, and it replaces the CLI steps people need most with typed tools.

What we're building

Decision
An APFM-owned MCP server, hosted as a Databricks App on the aplaceformom workspace. It serves curated skills and a small set of typed, read-only Databricks tools. Platform MCP is the main way users reach it.

The server

It's a Python service using the mcp SDK in stateless HTTP mode, which fits both the Apps proxy and Platform MCP's per-request model.

from mcp.server.fastmcp import FastMCP
from databricks.sdk import WorkspaceClient

mcp = FastMCP("apfm-databricks-skills", instructions=INDEX, stateless_http=True)

@mcp.tool()
def load_skill(name: str) -> str:
    """Load a Databricks skill's SKILL.md (with APFM notes)."""
    return read_skill(name)            # only names on the curated list

@mcp.tool()
def describe_table(full_name: str) -> dict:
    """Describe a Unity Catalog table as the calling user."""
    w = WorkspaceClient(token=user_token(), auth_type="pat")
    return w.tables.get(full_name).as_dict()

app = mcp.streamable_http_app()        # serves /mcp

read_skill opens files only inside the app's skills/ folder, so a crafted name can't read anything else. user_token() reads the user's token from the x-forwarded-access-token header. The repo would look like this:

apfm-databricks-skills-mcp/
  app.py            # MCP server and tools
  app.yaml          # uvicorn app:app on port 8000
  databricks.yml    # bundle: the app, CAN_USE grants, user_api_scopes
  skills/           # curated copy, written by the publish job
  overlay/          # APFM notes, LICENSE, NOTICE

Skill content and the publish job

A CI job pulls a pinned databricks-agent-skills release and keeps only the curated list. It adds the APFM note and license files, writes them into skills/, generates the skill index, and runs databricks bundle deploy. Updating skills means redeploying the app, with no Platform MCP release. Later, the content can move to a Unity Catalog volume so skills update without a redeploy and volume grants can split them into tiers.

The APFM note at the top of each skill tells the agent:

Behind Platform MCP: run SQL with databricks_call(workspace="aplaceformom", server="sql", tool="execute_sql_read_only") and ask data questions through the helix_care_* Genie servers. Where this skill says to run a CLI command, use the matching tool from the skills server if one exists, for example describe_table for databricks tables get. Steps with no matching tool, including deploy and write steps, need a local setup and aren't available through Platform MCP.

Access

  • Grant CAN_USE on the app to the same groups that hold the Databricks role in Platform MCP.
  • Declare only the user_api_scopes the typed tools need. A tool that needs a scope the app didn't request gets a 403.
  • Typed tools always run as the user, so Unity Catalog permissions and audit logs apply to the real person. The app's own service principal is used only to serve skill text.

Python SDK only

Every Databricks operation in the app goes through the Databricks Python SDK (databricks-sdk). The app doesn't install or run the Databricks CLI, not even as a fallback.

  • One tool per operation. Each tool calls a specific SDK method with typed parameters, and Platform MCP enforces a read or write level for it. A tool that accepts any command can't be gated this way, because Platform MCP only sees the tool name.
  • Runs as the user. Each call builds a WorkspaceClient from the forwarded user token, so Unity Catalog permissions and audit logs apply to the real person.
  • Nothing extra to ship. The SDK installs from requirements.txt, with no binary to package and no subprocess to manage.
  • Gaps. If a skill relies on an operation the SDK doesn't cover, we leave that step out of Platform MCP. The APFM note marks it as needing a local setup.

Platform MCP changes

  • Per-server URL override. The provider builds every upstream URL from the workspace hostname plus a path. The app lives on its own *.databricksapps.com domain, so servertypes.go and config.go need a way to set the base URL per server. This is the main code change.
  • A skills server type that allows the app's tools at their levels:
"skills": {
    PathTemplate: "/mcp",
    AllowedTools: map[string]string{
        "list_skills":    util.TierRead,
        "load_skill":     util.TierRead,
        "get_skill_file": util.TierRead,
        "list_catalogs":  util.TierRead,
        "describe_table": util.TierRead,
        // one entry per typed tool; write tools only after review
    },
},
  • Config in config.yaml, under workspaces.aplaceformom.servers:
skills:
  type: skills
  enabled: true
  base_url: "https://mcp-apfm-skills-<id>.aws.databricksapps.com"   # new field
  description: "APFM-curated Databricks agent skills and read-only tools"
  • Guidance. One line in the Databricks provider's guidance.md pointing agents at the skills server. The full index comes from the app's own startup instructions.
  • Tests that mirror the existing allowed-tool tests, and a new end-to-end case.

Rollout plan

  1. Spike the auth path

    Deploy a minimal MCP app in sandbox. Call it with a token issued by Platform MCP and confirm the app accepts it and receives the user's token. Confirm the naming convention for MCP apps.

    DPLAT with Data Platform · Done when a test call through Platform MCP reaches the app as the user

  2. Set up the app and bundle

    Create the repo, app.yaml and databricks.yml. Grant CAN_USE to the right groups and declare the user scopes.

    DPLAT, Data Platform · Done when the app runs and only granted users can reach it

  3. Serve the skills and build the publish job

    Add list_skills, load_skill, get_skill_file and the startup index. The job pins a release, curates, adds APFM notes and license files, then deploys the app.

    DPLAT · Done when a version bump in CI redeploys the app with new skills

  4. Add the first typed tools

    Build the read-only SDK tools listed above, each running as the user, with unit tests.

    DPLAT · Done when each tool returns the user's own view and fails cleanly on a 403

  5. Change Platform MCP

    Add the per-server URL override, the skills server type, the config entry, and the guidance line, with tests.

    DPLAT · Done when databricks_discover_tools lists the skills server and unknown tools are rejected

  6. Extend the end-to-end checks

    List skills, load databricks-dbsql, follow it to run a read-only query, and call describe_table.

    DPLAT · Done when the new e2e case passes in sandbox

  7. Document and announce

    Update the Databricks provider docs and the Platform MCP Getting Started page on Confluence, including the local-install path for engineers.

    DPLAT · Done when published and announced

FAQ

I use Claude Desktop. What changes for me?
Nothing to install. Once your Databricks account is linked in Platform MCP, Claude can look up a Databricks skill when your question calls for one, and use the read-only tools to check things like a table's schema or a job run's status.
I'm an engineer with the Databricks CLI. Should I stop using the plugin?
No. Keep the official plugin for building and deploying apps, jobs, pipelines, and bundles. Platform MCP covers governed, read-only work and is the only path for people without a CLI.
Why doesn't the app just run the Databricks CLI?
The app uses only the Python SDK. A tool that runs any command can't be gated safely, because Platform MCP only sees the tool name. One SDK tool per operation lets us allow reads, block writes, and review each new operation on its own.
Can our own teams add skills or tools?
Yes. APFM-written skills go into the same curated folder, and new tools are added by pull request to the app repo, with a review for anything that writes.
Does this give anyone new data access?
No. Skills are instructions, not data, and every tool runs as you, under your existing Unity Catalog permissions.
Why not load every skill into every session?
The full set is about 3.3 MB of text. Only the short index is always loaded. The agent pulls a full skill when it needs one.
